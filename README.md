# CRM Sales Opportunities Data Warehouse

A working 5-layer system:

```
source_data (XML/CSV) -> Java ETL -> MySQL warehouse -> PHP query engine -> HTML dashboard
```

## About the sample data

**Important:** `source_data/` contains a small, *synthetic* sample dataset
(20 accounts, 7 products, 10 sales agents, 300 pipeline rows), generated by
`source_data/generate_data.py`. It is **not** an official/real dataset — it
was built to be simple and to exercise the same kinds of data-quality issues
a real dataset like this would have:

- Inconsistent casing / a misspelling in `accounts.sector` ("technolgy" -> Technology)
- A typo in `accounts.office_location` ("Philipines" -> Philippines)
- A product-name typo in `sales_pipeline.product` ("GTXPro" -> "GTX Pro") that would
  otherwise fail the foreign-key constraint against `products`
- Genuine NULLs in `sales_pipeline` (no account yet, no engage_date yet, still-open deals
  with no close_date/close_value) — these are preserved as NULL, not fabricated

If your assignment supplies its own official dataset, replace the files in
`source_data/` with the real `accounts.xml`, `sales_teams.xml`, `products.csv`,
`sales_pipeline.csv` (matching the same file names and structure) and re-run the ETL.

## Project layout

```
source_data/                 accounts.xml, sales_teams.xml, products.csv,
                              sales_pipeline.csv, data_dictionary.csv, generate_data.py

ETL_Java/
  src/                        XMLParser.java, CSVParser.java, DataTransformer.java,
                              MySQLLoader.java, ETL_Main.java
  lib/                        mariadb-java-client.jar (JDBC driver)
PHP_Query_Engine/              config.php, queryEngine.php
Web_Interface/                 index.html (dashboard)
```

## 1. Set up MySQL/MariaDB

```bash
mysql -u root -p < Integrated_Data_Warehouse/schema.sql
```

This creates the `crm_warehouse` database and its 4 tables
(`accounts`, `products`, `sales_teams`, `sales_pipeline`).

Set/confirm the root password (the placeholder used throughout this project is `rootroot`,
matching most assignment briefs' convention — change it for anything beyond local dev):

```sql
ALTER USER 'root'@'localhost' IDENTIFIED BY 'rootroot';
FLUSH PRIVILEGES;
```

## 2. Compile and run the ETL

The JDBC driver (MariaDB Connector/J) is already bundled in `ETL_Java/lib/`.
On Debian/Ubuntu it can also be installed with `apt-get install libmariadb-java`.

```bash
cd ETL_Java/src
javac -cp ../lib/mariadb-java-client.jar *.java

java -cp .:../lib/mariadb-java-client.jar ETL_Main \../../source_data \"jdbc:mariadb://localhost:3306/crm_warehouse" \
     root rootroot
```

You should see extraction counts, a data-cleaning summary, and load counts,
ending with `ETL run completed successfully ... zero errors`.
Re-running it is safe — the loader truncates all four tables before every run.

## 3. Run the PHP query engine + web interface

```bash
cd /path/to/project   # the folder containing PHP_Query_Engine/ and Web_Interface/
php -S 127.0.0.1:8000
```

Then open: `http://127.0.0.1:8000/Web_Interface/index.html`

You can also hit the API directly, e.g.:

```bash
curl "http://127.0.0.1:8000/PHP_Query_Engine/queryEngine.php?report=products"
curl "http://127.0.0.1:8000/PHP_Query_Engine/queryEngine.php?report=opportunities&page=1"
curl "http://127.0.0.1:8000/PHP_Query_Engine/queryEngine.php?report=establishment_year"
curl "http://127.0.0.1:8000/PHP_Query_Engine/queryEngine.php?report=product_analysis"
```

An unrecognised `?report=` value returns HTTP 400.

## Dashboard

- **Products Report** — every product, series, and price
- **Sales Opportunities Report (Won/Lost)** — paginated table (25 rows/page),
  with KPI cards (win rate, total won value, etc.) computed from the full result set
- **Establishment Year Revenue Analysis** — bar chart of total account revenue by founding year
- **Sales Opportunity Analysis (by Product)** — bar chart of won revenue per product

## Notes for adapting to a real dataset

- If your real `accounts.xml` doesn't have the same field-name collision
  quirk baked into this sample (a leaf `<account>` element nested inside a
  record element also called `<account>`), `XMLParser.parseRecords()` still
  works correctly either way — it only reads direct children of the root, so
  it isn't relying on that quirk being present.
- Adjust `DataTransformer` if your real data has different messy values than
  the ones simulated here.
- Update `PHP_Query_Engine/config.php` with your actual DB credentials before
  deploying anywhere beyond local development.
